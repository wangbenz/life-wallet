## 1. 项目概述

### 项目名称

Life Wallet / 人生存钱罐 / 人生账本

### 核心理念

每个人每天都会“消耗 1 元人生”，但可以通过 AI 理解这一元是如何被使用的。

本产品不是记账工具，而是：

AI 人生理解系统（AI Life Understanding System）

### 核心问题

传统问题：

- 记录成本高
- 分类复杂
- 用户难以坚持
- 数据无法形成长期理解

### 产品目标

让用户只做一件事：

用自然语言描述一天发生的事情。

其余全部交给 AI：

- 理解
- 分类
- 结构化
- 长期分析
- 人生画像构建

## 2. 核心机制

### 2.1 人生余额机制（世界观）

```text
人生 = 固定总量
每天 = -1 元（不可逆）
```

特点：

- 不增加
- 不返还
- 不奖励
- 纯消耗模型

用于强化“时间不可逆”认知。

### 2.2 AI 记录机制

用户输入：

- 文字
- 语音（后续）

示例：

> 今天学了 Java 2 小时，练了英语口语 1 小时，晚上刷视频 2 小时

AI 自动生成：

- Activity（事件）
- 分类归因
- 时间分布
- 总结

用户只需确认（可选）。

### 2.3 核心原则

用户不应该做：

- 手动分类
- 选择标签体系
- 复杂结构整理

AI 负责：

- 分类
- 结构化
- 聚合
- 长期记忆
- 洞察生成

### 2.4 高频使用场景（阶段性结论）

理想场景是用户睡前复盘当天生活，但真实使用中不能假设用户一定会在晚上打开小程序。

Life Wallet 第一版需要支持以下真实记录方式：

- 当日复盘：当天晚上记录今天。
- 次日补录：第二天早上或中午记录昨天。
- 分段记录：中午记录上午，晚上记录下午或晚上。
- 模糊记录：用户用“上午都在工作”“昨天晚上刷了会视频”“今天基本都在开会”等表达描述生活片段。

阶段性产品原则：

> Life Wallet 不要求用户实时、精确记录，而是允许用户用自然语言补记生活片段；系统负责时间估算、分类和温和确认。

记录时间不等于发生时间。用户第二天记录“昨天晚上刷视频”，该记录仍应归到昨天晚上，而不是归到记录发生的当天中午。

### 2.5 模糊记录与估算原则（阶段性结论）

用户描述模糊时间时，系统可以根据自然语言进行估算，但不应伪装成精确记录。

示例：

```text
用户输入：今天上午都在工作

系统理解：
- 时间表达：今天上午
- 估算时长：约 3 小时
- Activity：工作
- Dimension：创造 / 生活（具体归类规则后续定义）
- Domain：工作
- 置信度：中
- 是否需要确认：是
```

置信度主要用于系统内部判断是否需要追问、确认和区分统计可靠性，不建议在 MVP 中直接以技术指标展示给用户。

面向用户的表达应保持自然，例如：

> 我先按“上午约 3 小时”记为工作，你可以直接确认或修改。

阶段性产品原则：

> Life Wallet 追求的是人生支出的可理解性，而不是分钟级时间审计的精确性。

### 2.6 核心痛点优先级（阶段性结论）

当前核心痛点优先级：

1. 记录成本高
2. 分类困难
3. 难以坚持
4. 缺少长期理解

第一优先级是记录成本高。Life Wallet 的所有后续价值都依赖用户愿意持续留下生活数据。如果记录复杂，用户可能只打开一次就放弃，后续 AI 分类、统计、反馈、周报和月报都无法产生。

阶段性产品原则：

> Life Wallet 的第一产品目标不是让统计更强，而是让记录足够轻。只要记录成本没有低到接近日常说话，产品就无法进入持续使用。

### 2.7 当前替代方案与不足（阶段性结论）

用户现在如果想知道“时间花在哪里、生活过得怎么样”，通常会使用以下替代方式：

| 替代方案 | 能解决什么 | 主要不足 |
|---|---|---|
| 备忘录 / 微信文件传输助手 / 随手记 | 快速记下一句话，记录成本低 | 后续不方便查看、分类和统计，难以形成周报或月报 |
| 日记 App / 手写日记 | 自由表达经历和感受 | 偏叙事，不会自动拆解活动、估算时间、归入人生维度 |
| 时间管理 App | 精确记录每件事花多久，统计能力强 | 记录成本高，需要频繁选择事项、分类、开始和结束时间，难坚持 |
| 打卡 / 习惯 App | 追踪学习、运动、早睡等固定行为 | 只能回答“有没有做某件事”，不能回答“这一元人生整体花到哪里” |
| Notion / Excel | 灵活，可自定义表格和统计 | 维护成本高，需要用户自己设计分类、填数据、做统计 |
| 手机屏幕使用时间 | 自动统计手机 App 使用时长 | 只能理解手机行为，不能理解线下生活、工作、学习、社交和运动 |

阶段性机会判断：

> 低成本记录的工具不擅长统计，擅长统计的工具记录成本太高；Life Wallet 的机会，是用自然语言输入 + AI 自动理解，把记录成本和长期统计同时做好。

### 2.8 前 7 天留存规则（阶段性结论）

前 7 天留存不应简单按自然周处理。用户可能周三开始记录，那么下周三看到的是“第一个 7 天记录周期”，而不是完整自然周。

新用户阶段建议按“记录日”或“最近 7 天”计算：

```text
第 1 天：人生余额冲击
第 2 个记录日：今日 1 元人生反馈
第 3 个记录日：最近几次记录开始形成对比
第 7 个记录日：生成第一份最近 7 天人生账单
```

阶段性产品原则：

> 新用户留存周期按“记录日”计算，不按自然周计算；成熟用户统计再支持自然周、自然月。

### 2.9 产品边界（阶段性结论）

Life Wallet 的核心不是“管理人生”，而是帮助用户低成本记录生活，并把时间消耗转化为可理解的人生账单。

因此，Life Wallet 第一版不应变成以下产品：

| 不是 | 边界说明 |
|---|---|
| 传统记账工具 | 不记录金钱收入、支出、预算、资产和负债；“账单”只用于表达时间和人生支出 |
| 任务管理工具 | 不管理待办、截止日期、项目进度或提醒执行 |
| 打卡 / 习惯工具 | 不以连续打卡、成就、积分或惩罚驱动用户 |
| 精确时间审计工具 | 不要求分钟级计时、开始结束时间或全天无遗漏记录 |
| 社交排名产品 | 不做用户之间的人生分数、排行榜、PK 或攀比 |
| 心理治疗产品 | 不诊断、不治疗、不处理危机干预，不替代专业心理咨询 |
| 强说教型人生教练 | 不主动给用户下命令，不用羞耻感驱动改变 |
| 全量个人数据中台 | 不在第一版接入所有日历、定位、健康、屏幕时间和第三方数据 |

第一版明确不做：

- 不做金钱记账、预算和资产管理。
- 不做待办事项、任务拆解、日程管理和项目管理。
- 不做社交发布、好友比较、排行榜和用户间排名。
- 不做积分、奖励、成就徽章、连续打卡惩罚。
- 不做分钟级计时器或强制用户补齐全天时间。
- 不做心理诊断、治疗建议和危机判断。
- 不做强主动建议系统；反馈以理解、总结和温和提醒为主。
- 不做复杂自定义分类；用户不需要配置 Dimension / Domain / Topic。
- 不做大量外部数据集成；先验证自然语言记录闭环。

阶段性产品原则：

> Life Wallet 第一版只服务一个核心闭环：自然语言记录生活 → AI 理解和估算 → 生成人生支出反馈 → 帮助用户看见自己的生活分布。

任何不能强化这个闭环、反而增加记录成本或改变产品心智的能力，都不应进入第一版。

### 2.10 关键假设与验证方式（阶段性结论）

Product Discovery 当前需要验证的不是“能不能做出功能”，而是这些产品判断是否成立。

| 假设 | 为什么关键 | 建议验证方式 |
|---|---|---|
| 目标用户愿意用自然语言持续记录生活 | 如果用户不愿持续输入，AI 分类、统计、周报和月报都不会产生 | 找 5-10 个目标用户进行 7 天手工试用；每天只要求发一段自然语言记录 |
| 记录成本可以低到接近日常说话 | 第一优先级痛点是记录成本高，输入体验决定留存 | 观察用户每天记录所需时间、是否需要提醒、是否觉得麻烦 |
| AI 对模糊时间和生活片段的估算足够可信 | 产品不追求分钟级精确，但结果必须让用户觉得“基本像我” | 用真实记录样本人工模拟解析，让用户确认分类和估算是否可接受 |
| “1 元人生”表达不仅有首次冲击，也能支撑持续理解 | 如果只是一次性噱头，长期留存会不足 | 访谈用户看到日 / 7 天账单后的感受，确认是否帮助其理解生活分布 |
| Life Dimension 七类足够承载早期统计 | 一级分类是长期统计基础，过粗或过细都会影响理解 | 用真实样本做归类测试，记录难归类活动和用户困惑点 |
| 日 / 最近 7 天 / 月反馈能形成回访理由 | 留存闭环依赖不同周期的反馈价值 | 手工生成第 2、3、7 个记录日反馈，询问用户是否愿意继续看 |
| 温和反馈比强建议更适合第一版 | 产品边界要求不说教、不治疗，但反馈仍需有价值 | 对比“总结型反馈”和“建议型反馈”的用户接受度 |

验证优先级：

1. 用户是否愿意连续 7 个记录日留下自然语言记录。
2. 用户是否接受 AI 对模糊生活片段的分类和估算。
3. 用户是否觉得“人生账单”反馈值得第二天继续回来。

阶段性产品原则：

> 第一版最需要验证的是记录闭环和反馈闭环，而不是完整功能数量。只要用户不愿持续记录，后续统计、画像、Memory 和 Agent 能力都没有验证基础。

### 2.11 Product Discovery 收束判断（阶段性结论）

根据 Discovery Checklist 当前完成度，Life Wallet 已具备进入 Product Definition 草案的基础。

当前已回答的问题：

- 第一批目标用户是谁。
- 用户在什么场景下记录。
- 最重要的痛点是什么。
- 当前替代方案是什么，为什么不足。
- 用户为什么首次打开，以及为什么在第 2 / 3 / 7 个记录日回来。
- 产品核心价值闭环是什么。
- 第一版不是什么、不做什么。
- 哪些关键假设必须验证。

当前仍然不是已经完成真实验证，而是完成了 Discovery 文档收束。需要保留的风险：

| 风险 | 说明 | 后续处理 |
|---|---|---|
| 持续记录意愿未验证 | 用户可能认可理念，但无法坚持 7 个记录日 | 用 5-10 个目标用户做 7 天手工验证 |
| AI 估算可信度未验证 | 模糊记录可能让用户觉得“不像我”或“不准确” | 用真实样本做人工作业式解析，让用户确认 |
| 世界观持续价值未验证 | “1 元人生”可能只有首次冲击 | 对比第 1 天、第 3 天、第 7 天反馈后的用户感受 |
| 反馈语气未验证 | 过强会说教，过弱会无用 | 对比总结型、提醒型和建议型反馈 |

阶段性判断：

> Product Discovery 可以在文档层面阶段性收束，下一步进入 Product Definition 草案；真实用户验证不阻塞写定义文档，但会影响 MVP Design 的取舍和成功标准。

## 3. 分类体系设计

### 3.1 分类分层

#### 第一层：Life Dimension（固定）

系统级稳定维度：

- 成长
- 创造
- 关系
- 健康
- 生活
- 休闲
- 睡眠

用于长期统计，不变化。

#### 第二层：Domain（半动态）

AI 维护的领域：

- 代码
- 英语
- 金融
- AI
- 写作
- 运动

特点：

- 可扩展
- 可合并
- 可演化

#### 第三层：Topic（完全动态）

用户真实行为主题：

- Java
- Python
- 口语
- 雅思
- Spring Boot

特点：

- 不建固定表
- 仅作为语义标签
- 支持未来 embedding / 聚类

### 3.2 关键设计原则

- 用户不接触分类系统
- 不暴露三级结构
- 全部由 AI 自动生成
- 分类允许演化，尤其是 Domain

## 4. AI Agent 设计

### 4.1 Agent 职责

AI 不只是分类器，而是负责：

- 理解用户输入
- 提取 Activity
- 生成分类结构
- 计算时间分布
- 输出总结
- 形成长期记忆

### 4.2 输入输出流程

```text
用户自然语言
      ↓
LLM解析
      ↓
Activity抽取
      ↓
Dimension归因（固定）
      ↓
Domain归因（动态）
      ↓
Topic生成
      ↓
结构化记录
      ↓
用户确认（可选）
      ↓
入库
```

### 4.3 AI 输出结构（建议）

```json
{
  "activities": [
    {
      "title": "学习 Java",
      "duration": 120,
      "dimension": "成长",
      "domain": "代码",
      "topic": "Java"
    }
  ],
  "summary": "今天成长投入较多，学习为主"
}
```

## 13. Discovery Checklist 当前核对

### 13.1 目标用户

当前初步结论：

一二线城市上班族中，对生活需要数据化指标，并希望通过记录、分析和反馈来调整自己的人。

用户特征：

- 对生活质量、时间使用、成长投入有焦虑或追求。
- 能接受数据化反馈。
- 愿意通过低成本记录换取分析。
- 不一定愿意手动记账、打卡、分类。
- 更在意“我这段时间到底把人生花在哪里了”。

### 13.2 首次打开动机

“每天 1 元人生”不是核心功能本身，而是世界观入口和强记忆点。

首次进入建议流程：

```text
输入生日 + 预计寿命
  ↓
生成人生账户余额
  ↓
用户直观看到：人生账户不是无限的
  ↓
进入记录、分析和反馈的核心功能
```

这个入口的目标是制造一次认知冲击：用户意识到自己的人生账户余额有限，从而更愿意珍惜每天时间。

### 13.3 1 元人生的时间换算规则

```text
1 天 = 1 元人生
24 小时 = 1 元人生
1 小时 = 1/24 元人生
```

示例：

```text
本月英语学习 48 小时 = 2 元人生
本周运动 7 小时 ≈ 0.29 元人生
今天刷视频 3 小时 = 0.125 元人生
```

该规则将普通时间统计转化为“人生支出”反馈。

### 13.4 核心记录与反馈闭环

```text
人生余额冲击
  ↓
自然语言 / 语音记录一天
  ↓
AI Agent 自动分类
  ↓
换算为人生支出
  ↓
饼图展示 Life Dimension 占比
  ↓
个人支出排行展示具体支出方向
  ↓
日 / 周 / 月反馈帮助用户调整生活
```

### 13.5 每日 / 每周 / 每月统计

每日反馈：

- 展示今日 1 元人生如何被消耗。
- 使用 Life Dimension 饼图展示一级分类百分比。
- 使用 AI 一句话总结解释今日分布，而不是简单判断好坏。

每周反馈：

- 展示一周 Life Dimension 分布。
- 发现生活模式，例如成长投入、休闲占比、睡眠不足、关系投入偏少等。

每月反馈：

- 展示本月人生支出排行。
- 形成阶段性人生画像。
- 帮助用户识别值得保留或需要调整的行为模式。

### 13.6 个人支出排行

排行榜应优先做成“个人人生支出排行”，而不是用户之间的社交排名。

示例：

```text
本月人生支出 Top 5
1. 英语学习：2.0 元人生
2. 工作项目：1.6 元人生
3. 短视频休闲：1.2 元人生
4. 运动：0.5 元人生
5. 陪伴家人：0.4 元人生
```

个人支出排行回答的问题是：这段时间，我的人生主要花在了哪些事情上？
