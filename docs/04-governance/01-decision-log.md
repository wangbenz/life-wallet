## Decision-001: 每天固定扣除 1 元人生

人生余额是纯消耗模型。每天固定扣除 1 元，不增加、不返还、不奖励。

## Decision-002: 用户不进行任何手动分类

用户只输入自然语言，不选择分类、标签或复杂结构。

## Decision-003: AI 负责全部结构化理解与分类

AI 负责从自然语言中提取 Activity、归因 Dimension / Domain / Topic，并生成总结。

## Decision-004: 一级分类 Life Dimension 固定

Life Dimension 是长期统计用的系统级稳定维度，当前包括：成长、创造、关系、健康、生活、休闲、睡眠。

## Decision-005: Domain 可演化

Domain 由 AI 维护，允许新增、合并、调整。

## Decision-006: Topic 不作为数据库固定结构

Topic 仅作为语义标签，未来可用于 embedding、聚类和长期画像。

## Decision-007: 用户输入必须使用自然语言

MVP 支持文字输入，语音输入后续加入。


## 2026-07-07：目标用户初步聚焦为一二线城市数据化生活上班族

### 类型

Product Decision

### 背景

Product Discovery 阶段需要先明确第一批目标用户，避免产品变成泛人群工具。

### 最终决策

Life Wallet 第一批目标用户初步聚焦为：一二线城市上班族中，对生活需要数据化指标，并希望通过记录、分析和反馈来调整自己的人。

### 决策原因

这类用户更容易理解时间账户化、数据反馈、日周月统计和 AI 分析的价值，也更可能接受自然语言记录换取生活洞察。

### 后续待确认

需要继续验证该用户群的真实记录意愿、付费意愿和连续使用动机。

## 2026-07-07：1 元人生定位为世界观入口与时间账户化表达

### 类型

Product Decision

### 背景

“每天 1 元人生”可能被误解为积分或奖励系统，需要明确其产品定位。

### 最终决策

1 元人生不是奖励系统，而是世界观入口与时间账户化表达。它用于吸引用户首次打开、强化时间稀缺感，并将行为统计转化为“人生支出”反馈。

### 决策原因

相比普通时间统计，“本月英语学习 48 小时 = 2 元人生”更有产品记忆点，也更符合 Life Wallet 的账户隐喻。

### 影响范围

- 首次进入需要输入生日和预计寿命，生成人生账户余额。
- 日 / 周 / 月统计可以使用人生支出作为表达单位。
- 不引入奖励、返还、积分化机制。

## 2026-07-07：日 / 周 / 月反馈作为早期留存闭环

### 类型

Product Decision / UX Decision

### 背景

产品需要回答用户为什么持续使用，而不仅是为什么第一次打开。

### 最终决策

Life Wallet 必须具备日 / 周 / 月三个反馈周期：每日即时理解、每周模式洞察、每月人生画像。

### 决策原因

每日反馈提供即时回报；每周反馈帮助用户看见生活模式；每月反馈形成长期理解和阶段性画像。

### 影响范围

- 每日：1 元人生分布、Life Dimension 饼图、AI 总结。
- 每周：维度趋势、生活模式发现。
- 每月：人生支出排行、阶段性画像。

## 2026-07-07：每日核心视觉表达采用 Life Dimension 饼图

### 类型

UX Decision / Product Decision

### 背景

用户需要快速理解“今天这一元人生被花在哪里”。

### 最终决策

每日反馈围绕“今日 1 元人生如何被消耗”展开，并用 Life Dimension 百分比饼图作为核心视觉表达。

### 决策原因

Life Dimension 是固定一级分类，适合做长期统计和直观展示。饼图负责看见分布，AI 总结负责理解含义。

### 后续待确认

需要继续确定饼图旁边 AI 总结的语气、结构，以及是否允许出现质量判断。

## 2026-07-08：真实记录场景支持延迟、补录、分段和模糊表达

### 类型

Product Decision / UX Decision / Agent Decision

### 背景

睡前复盘是理想使用场景，但真实用户不一定会在晚上打开小程序，也可能在第二天早上、中午或任意碎片时间补记。

### 最终决策

Life Wallet 不要求用户实时、精确记录，而是允许用户用自然语言补记生活片段，包括当日复盘、次日补录、分段记录和模糊时间表达。

### 决策原因

真实记录行为天然存在延迟和不完整。如果产品强迫用户精确选择时间段或实时记录，会显著提高记录成本，削弱持续使用。

### 影响范围

- 记录时间不等于发生时间。
- AI 需要理解“今天上午”“昨天晚上”“刚才”“最近几天”等自然语言时间。
- 对模糊记录可以进行估算，并在必要时温和确认。

## 2026-07-08：核心痛点第一优先级确定为记录成本高

### 类型

Product Decision

### 背景

Life Wallet 的 AI 分类、统计、反馈、周报和月报都依赖用户持续留下生活数据。

### 最终决策

核心痛点优先级初步确定为：记录成本高、分类困难、难以坚持、缺少长期理解。其中记录成本高是第一优先级。

### 决策原因

如果记录复杂，用户可能只打开一次就放弃，后续产品价值无法产生。因此第一产品目标不是让统计更强，而是让记录足够轻，接近日常说话。

## 2026-07-08：替代方案不足来自低成本记录与强统计能力无法兼得

### 类型

Product Decision

### 背景

用户现有替代方案包括备忘录、日记、时间管理 App、打卡工具、Notion / Excel、手机屏幕使用时间等。

### 最终决策

Life Wallet 的机会不是“也能记录”，而是让用户像写备忘录一样轻松记录，同时让系统像时间管理工具一样自动分类统计，并进一步形成日 / 周 / 月的人生理解反馈。

### 决策原因

低成本记录工具不擅长后续查看、分类和统计；统计能力强的工具记录成本过高，难以坚持。

## 2026-07-08：新用户前 7 天按记录日而非自然周计算

### 类型

Product Decision / UX Decision

### 背景

用户可能在周三、周五或任意日期开始记录。若直接使用自然周，会导致第一份“一周报告”并不完整。

### 最终决策

新用户留存周期按“记录日”或“最近 7 天”计算，不按自然周计算。第 7 个记录日生成“第一份最近 7 天人生账单”，不称为“本周账单”。

### 决策原因

这样可以避免自然周边界造成的理解偏差，并让新用户无论从哪一天开始，都能获得完整的首个 7 天反馈。

### 影响范围

- Onboarding 阶段优先使用“最近 7 天人生账单”。
- 成熟使用后再支持自然周、自然月统计。

## 2026-07-08：第一版产品边界聚焦自然语言人生账单闭环

### 类型

Product Decision / UX Decision / Agent Decision

### 背景

Life Wallet 容易被相邻产品形态拉偏，例如记账、任务管理、打卡习惯、时间审计、心理咨询、社交排名或全量个人数据分析。Product Discovery 阶段需要提前明确边界，避免第一版范围膨胀。

### 最终决策

Life Wallet 第一版只服务一个核心闭环：自然语言记录生活 → AI 理解和估算 → 生成人生支出反馈 → 帮助用户看见自己的生活分布。

第一版明确不做传统金钱记账、任务管理、打卡积分、分钟级计时、社交排名、心理治疗、强主动建议和大量外部数据集成。

### 决策原因

当前第一优先级痛点是记录成本高。任何增加用户操作成本、改变产品心智或引入高风险责任边界的能力，都会削弱第一版验证重点。

### 影响范围

- 产品定义阶段需要继续围绕“自然语言记录 + AI 理解 + 人生支出反馈”收束。
- MVP Design 阶段不应引入任务、打卡、社交、心理治疗或复杂集成模块。
- Agent 能力边界以理解、总结和温和反馈为主，避免诊断、治疗、命令和羞耻感表达。

## 2026-07-08：H5 Demo 作为当前 MVP 验证载体

最终目标是微信小程序，但当前还处于 MVP Design 阶段。直接先做小程序会引入开发者工具、体验版、测试成员、真机调试和微信生态能力等额外复杂度，可能拖慢核心流程验证。

## 2026-07-08：H5 Demo 第一版采用单页流程

### 类型

UX Decision / Product Decision

### 背景

H5 Demo 的目标是快速验证核心流程，而不是设计完整产品导航。如果第一版拆成多个页面，会增加实现成本和测试路径复杂度。

### 最终决策

H5 Demo 第一版采用单页分区流程：

```text
人生账户区
  ↓
今日记录区
  ↓
AI 解析 / 今日账单区
  ↓
用户反馈区
```

### 决策原因

单页流程更适合快速测试“记录 → AI 解析 → 今日人生账单反馈”的最短闭环，也方便观察用户是否能顺利完成从输入到理解反馈的完整过程。

### 影响范围

- MVP Design 文档补充单页交互细节。
- 第一版 H5 Demo 不做复杂导航和多页面信息架构。
- 后续 Architecture 可以先围绕单页 H5 Demo 设计最小技术方案。

### 后续状态

该决策已被后续“多 Tab 结构”修正。保留本条记录用于说明方案演进过程。

## 2026-07-08：H5 Demo 第一版改为多 Tab 结构

### 类型

UX Decision / Product Decision

### 背景

单页流程虽然实现快，但容易变成长页面，手机上展示不完整，也不符合用户对类小程序产品的预期。最终目标是微信小程序，因此 H5 Demo 更适合提前采用接近小程序的页面结构。

### 最终决策

H5 Demo 第一版采用多页面 + 底部 Tab 菜单结构：

```text
首页｜账单｜我的
```

首页负责人生余额、剩余人生展示、今日状态和记录入口；账单页负责今日人生账单、维度分布、Activity 明细和结果反馈；我的页负责生日和期望寿命设置。

### 决策原因

多 Tab 结构更接近最终微信小程序形态，用户更容易理解，后续迁移到小程序时页面结构也更容易复用。

### 影响范围

- MVP Design 文档从单页流程调整为多 Tab 页面结构。
- 后续 H5 Demo 架构需要支持前端路由或 Tab 状态切换。
- 当前仍不进入应用代码，直到 MVP Design 和 Architecture 明确。

### 后续状态

Session 002 后，该方案被识别为仍偏传统小程序思维，需要围绕 Agent First Prototype 重新设计。

## Decision-008: Agent 是产品主入口

### Status

Proposed

### 内容

Agent 应作为 Life Wallet 的产品主入口。

用户进入产品后，不应先寻找“记录按钮”或统计入口，而是直接向 Agent 表达今天发生了什么、最近怎么样、想复盘什么。

### 原因

Life Wallet 的核心不是页面，而是：

```text
用户 → Agent → Memory → Insight
```

如果入口仍然以传统功能页面为中心，产品会退回“带 AI 的小程序”，而不是 AI Native 产品。

## Decision-009: 首页采用 Agent First 设计

### Status

Proposed

### 内容

首页不再以功能入口、统计图和按钮为中心，而应以 Agent First 方式呈现：

```text
人生余额
今日 1 元人生
Agent 对话
AI 理解
今日总结
```

### 原因

用户每天最重要的动作不是进入某个功能模块，而是自然表达和复盘今天这一元人生花到了哪里。

## Decision-010: Dashboard 不作为核心价值，Insight 高于统计图

### Status

Proposed

### 内容

Dashboard、饼图、折线图、柱状图等统计展示不作为 Life Wallet 的核心价值。

图表可以作为辅助证据，但核心价值应是 Agent 基于用户记录、Memory 和趋势生成 Insight。

### 原因

AI Native 产品中，用户更关心“我最近怎么样”“我该如何理解自己的状态”，而不是主动阅读一堆仪表盘。

## Decision-011: Agent 不定位为通用聊天机器人

### Status

Proposed

### 内容

Life Wallet Agent 不定位为百科、搜索引擎或万能助手。

Agent 可以处理：

- 每日记录。
- 修改记录。
- 人生总结。
- 长期分析。
- 成长建议。
- 时间分配。
- 情绪理解。

原则上不处理与当前人生记录和用户上下文无关的通识问题。

### 原因

如果 Agent 什么都回答，产品会逐渐失焦，变成一个普通 ChatGPT 入口。

## Decision-012: Agent 的能力边界由用户当前 Context 决定

### Status

Proposed

### 内容

Agent 是否回答一个问题，不只看问题类型，而要看问题是否与用户当前人生上下文相关。

上下文包括：

- 当天记录。
- 近期记录。
- 用户目标。
- 学习内容。
- 工作内容。
- 健康状态。
- 长期 Memory。

### 原因

同一个问题在不同上下文下边界不同。

例如 `HashMap 为什么线程不安全？` 通常是通识技术问题，但如果用户最近正在记录 Java 学习，它就可能是当前成长上下文的一部分。

## Decision-013: 第一版先实现自定义轻量 Life Agent，暂不重度依赖 LangChain4j

### Status

Proposed

### 内容

第一版 Agent 采用 Spring Boot 自定义工作流实现，而不是直接使用 LangChain4j 的 Agent 编排能力。

核心流程包括：

1. IntentRecognizer：识别用户意图。
2. ActivityExtractor：抽取用户活动。
3. LifeOntologyClassifier：归入 Life Dimension / Domain / Topic。
4. MemoryUpdater：更新用户长期记忆。
5. InsightGenerator：生成今日理解与反馈。

LangChain4j 第一阶段最多只作为 LLM 调用封装、Prompt 管理或结构化输出工具使用，不作为 Agent 核心编排框架。

### 原因

本项目的一个重要目标是帮助开发者学习 Agent 开发。

如果第一版直接使用 LangChain4j 等 Agent 框架，框架会隐藏很多关键过程，例如用户意图如何识别、多步骤任务如何拆解、LLM 输出如何校验、何时调用工具、何时更新 Memory、如何处理异常输入、如何控制 Agent 边界。

因此，第一版应优先手写一个可理解、可调试、可替换的轻量 Life Agent 工作流。

### 后续演进

- Phase 1：自定义轻量 Life Agent，理解 Agent 基础流程。
- Phase 2：引入 LangChain4j 管理 LLM 调用、Prompt、结构化输出。
- Phase 3：当 Tool Calling、Memory、RAG、多步骤编排变复杂后，再评估 LangChain4j Agent 能力。
- Phase 4：根据实际复杂度决定是否保留自定义编排，或迁移到框架化 Agent。

### 约束

在 Phase 1 中，不允许为了“更快实现”而直接把核心流程隐藏在框架中。

代码结构必须显式体现 Agent 的关键步骤。

## Decision-014: Activity v0.1 采用意义优先的轻量记录规则

### Status

Confirmed

### 内容

第一版中，Activity 定义为：

> 用户生活中可被记录、理解、归类的一段行为或状态。

Activity 不要求精确到分钟，也不要求覆盖用户一天中的全部时间。

值得记录的不是“所有事情”，而是会影响用户理解一天的事情。

默认记录：

- 工作、学习、健康、关系、生活、休闲、睡眠。
- 重要状态，例如疲惫、焦虑、专注、低落、有成就感。
- 重要思考，例如反思、计划、人生选择、长期目标相关想法。

默认不单独记录：

- 倒水、开门、刷牙 2 分钟、走到电梯口等过碎动作。

例外：

如果用户特别表达某件小事有意义，Agent 应尊重用户表达，将其作为可记录内容。

### 一天定义

第一版中，“一天”不严格等于自然日 `00:00-24:00`。

Agent 应优先尊重用户自然表达：

- “今天”归入用户当前语境下的今天。
- “昨天晚上”归入昨天。
- “凌晨一点才睡”通常归入前一天晚上的生活节奏。

记录时间不等于发生时间。

### 原因

Life Wallet 的目标不是做时间审计，而是帮助用户理解人生。

如果 Activity 粒度过细，用户会感到记录负担过重；如果粒度过粗，Agent 又难以生成有价值的 Insight。

因此第一版采用“用户回看时是否觉得有意义”作为 Activity 粒度标准。

## Decision-015: 第一版进入 H5 Agent Demo 开工边界

### Status

Confirmed

### 内容

第一版不继续扩大 Product Discovery，改为进入短平快的 H5 Agent Demo 实现。

第一版一句话：

> 用户设置生日和预期寿命后，在 Today 页和 Agent 对话记录今天，系统解析 Activity、分类、生成今日人生账单和总结；Life / Me 只做最小可用。

当前确认的页面结构：

```text
Today（Agent）｜Life（人生）｜Me（我的）
```

当前确认的技术路线：

- H5 Frontend。
- Spring Boot Backend。
- MySQL。
- 简单 LLM 调用封装。
- 自定义轻量 Life Agent 工作流。

### 第一版明确不做

- 完整微信小程序。
- 微信登录。
- 复杂长期 Memory。
- RAG。
- 向量数据库。
- Redis。
- 周报 / 月报。
- 支付和商业化。

### 原因

项目目标是尽快做出可运行的 Agent 产品 Demo，用真实体验验证核心闭环。

继续大范围讨论 Product Discovery 会拖慢进度；当前产品边界已经足够支撑最小实现，应先进入代码阶段。
